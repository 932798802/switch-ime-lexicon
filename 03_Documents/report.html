2 · 已验证：emuMMC raw NAND 不可直接解析

区域状态证据
LBA 0–33（MBR + GPT）明文成功解出 11 个分区（SYSTEM 2684 MB / USER 27917 MB）
PRODINFO密文该分区本身加密，属正常
SAFE / SYSTEM / USER 头部密文4 KB 熵 5.90，非明文 FAT 引导扇区
SYSTEM 分区末尾扇区全 0未写入区域未加密
判定依据：SYSTEM 与 USER 分区的头 32 字节完全相同，说明存在按「分区内扇区号」做 tweak 的逐扇区加密， 而未写入扇区保持全 0。这既非原始 eMMC 明文（否则可直接读 FAT），也非全盘加密。
结论：走 NAND raw 提取系统 title 的路不通（需 per-console 密钥，而 PRODINFO 本身也是密的）。 可行路径是固件包——它的 NCA 只受 NCA 层加密，与分区加密无关。

3 · 已验证：NCA 解密链路（本次打通）

本机无 hactool，全部自研实现。所有参数以 hactool 源码为准（nca.c / nca.h / utils.h / aes.c），不靠猜测。

项正确做法踩过的坑
头部解密前 0xC00 字节整体 AES-XTS，tweak = BE(sector)，sector 从 0 起曾误以为 magic 在文件 0x200
media_to_realblock × 0x200（不加 0xC00）多加 0xC00 导致末段越界
section 偏移FS header 在 header 块内 0x400 + i×0x200；section 数据区不含 FS header曾把数据区开头当 PFS0 magic，据此误判「解不开」
key indexmax(0x206, 0x220) − 1直接用 0x220 会差一代 —— 最初解不开的主因
key areaAES-ECB-Dec(key_area_key_<name>_<idx>, encrypted_keys[4][0x10])曾把派生方向的 DEC 写成 ENC
data key固定取 decrypted_key_area[2]（CRYPT_CTR）—
CTR IVreverse(section_ctr[0:8]) ∥ BE(section_offset ≫ 4)双段拼接，任何单一猜测都命中不了
CTR 递增128 位大端计数器—
关键推论：swkbd 的 0x220 = 0x16 → key index 0x15 → 用 key_area_key_application_15。而这份实机 keyset 恰好覆盖到 _15（没有 _16）， 所以 swkbd 可以解开——不需要 master_key_16。

8 · 三痛点可改性判定

痛点判定依据成本
① 按键位置不好 理论可改，工程很重 布局在 lyt/*.szs（Yaz0+SARC+bflyt 二进制 UI 格式），可 LayeredFS 替换 需 Yaz0 编码器 ＋ SARC 打包 ＋ bflyt 编辑器（SwitchLayoutEditor 量级）＋ 实机回归
② 联想功能不行 不可改 联想逻辑编译在 main 内；无语言模型，只有用户历史词典 —
③ 没有游戏词库 无可换之物 swkbd 无任何词典数据（RomFS 与 main 均已证实） —
额外事实：swkbd 不支持中文输入。用户「用起来很难受」的感受，本质是「连中文输入都没有」。

9 · 第三方输入法路线可行性

路线结论硬约束
sysmodule 做 am 层 mitm 只能改参数，造不出输入法 appletAE 的 Open*Proxy 命令对 sysmodule 不可用，无法代替游戏发起 swkbd 调用
LayeredFS 替换 swkbd 本体 唯一能交付真输入法的路 工作量数人月；swkbd 崩溃 → 全系统键盘失效
零开发替代 先做实测 改系统语言 ＋ 实测目标游戏的实际可输入集，受调用方 KeyboardConfig 限制

先例：uLaunch（开源重写 qlaunch，titleId 0100000000001000，配套 uSystem / uMenu / uLoader / uManager、Pixie / Plutonium UI 库）。
