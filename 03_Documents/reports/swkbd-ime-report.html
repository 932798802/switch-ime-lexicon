结论先行

Switch 的输入法不是「一个 applet」，而是三段式结构：swkbd（界面与宿主，titleId 0100000000001008）＋ OMRON iWnn 1.16.2（输入引擎，编译在 swkbd 的 main 内） ＋ 独立词典 title（数据，0100000000000805 / 0100000000000808）。

  1. 「没有游戏词库」的落点是真实存在的 —— 词库是独立 title 里的普通 RomFS 文件 （njtan.a / njubase*.a 等，共 17.25 MB 中文＋韩文、18.67 MB 日文＋欧美）。 上一版报告判「没有词库可换」是错的，因为它只在 swkbd 自己的 RomFS 里找。 而且可以覆盖：swkbd 取词典走 OpenDataStorageByDataId， 这正是 Atmosphere fs.mitm 会套 LayeredFS 的路径（源码级证据见 §5.5）。
  2. swkbd 22.5.0 确实支持中文输入 —— 简体（拼音 GB2312/GB18030）、繁体（注音 / 仓颉 / 速成 / 粤拼 / 笔画）、 韩文、日文。上一版依据一份被截断的文本表判「没有中文」，错的。
  3. 「联想差」有量化解释 —— 中文预测词典 njexyomi.a 只有 1.5 KB， 是近乎空壳的占位文件；日文同类文件 94 KB，而日文主词典 4.89 MB。这是「候选词贫弱」的直接原因。
  4. 「键位不好」可改但工程重 —— 布局是 bflyt 二进制资源（lyt/*.szs）， 且逻辑键位映射在代码里；改图不改行为。
  5. （v4 新增）私有格式 NJDC 已 100% 解出，并已实际生成可用词典 —— 读→写往返重建 零语义差异；据此生成的 150,000 条中文拼音词典 （含 252 条游戏词表）原版条目零丢失、全部结构校验通过。 部署包与验证方法见 dist/README.md，规范与证据见 §6.6。
  6. （v5 新增）已实机验证生效 —— 覆盖 njubase3.a 后， 真机上能打出原版词典里根本没有的词。路线从「源码级成立」升级为 最高等级证据：实机跑通。附带确认：整个文件连版式一起换掉（extra → clean）引擎照常接受， 说明 iWnn 完全按文件自身头部字段寻址。
  7. （v6 新增）修掉一个真 bug，并做出可用的简拼（首字母联想） —— 产物曾含 4,316 个重复键（打 ling 时候选里「零」出现 3 次）， 已修，五份产物重复数归零且原版条目零丢失； 另生成 简拼包（sljt → 杀戮尖塔），并 于 2026-09-27 实机验证通过 —— 连纯数字 0000、非音节串 zzzz 都能命中，说明引擎对读法形态零校验。详见 §6.7。

词典文件格式（已验证）

全部 nj*.a / nj*.ad1 以魔数 NJDC 开头，大端序：

0x00  "NJDC"
0x04  u16 version      （1 = exyomi 类，2 = base/tan 类）
0x08  u32  0x00040000 / 0x00050000
0x0C  u32  ≈ 数据段长度
0x10  u32  header_size （base 类 0x54，exyomi 类 0x3C）
0x14  u32 / 0x18 u32 / 0x1C u32   各段计数

这是 iWnn 的私有索引容器（trie ＋ 记录库），不存在「丢一个 txt 就生效」的入口。 要加词，必须先能生成合法的 NJDC。

6.5 · 「能不能插入第三方词典？」（v3 追加实测）

一句话：能，但只有一种装法 —— 覆盖已有的 NJDC 文件（把自己写的词库编成 NJDC）， 不能新增文件、也没有「用户词典」入口。

引擎有这能力，但 Switch 版没开

层面事实
iWnn 引擎 词典分 8 类：Integrated / Single Kanji / Ancillary Word / User / Learning / Rule / Customized / No Reading Prediction。Android 版 Wnn Keyboard Lab 明确支持「追加词典」（/sdcard/wnnlab/）→ 引擎有该能力。
Switch 版 swkbd main.rodata 里硬编码了完整词典文件名清单： njubase1/2/3.a|.ad1、njtan.a|.ad1、njexyomi.a|.ad1、 njcon.a、njcode.a、njcangjie.a、keisei/…、 变体 njubase1us.a/pt/br/gb。
而 njuser/usrdic/userdict/wdic/ learning/njaddon 等 42 个关键词在三段里零命中。
→ 无用户词典入口、无学习词典持久化（这也是 NS 输入法「不记事」的原因）； 塞新文件名不会被加载，只能改已有文件。

  • .ad1 的魔数是 NJAD（非 NJDC）：内部在 0x28 处 再嵌一个完整 NJDC，其头部与主词典逐字节相同 → 它是附属 / 变体，不是独立词典。 先只覆盖 30 KB 的 .ad1、保留 .a 不动，爆炸半径最小（且可随时删掉文件回滚）。

两条关键结论
① 引擎对读法形态零校验。原先最担心的「引擎按音节切分 → 辅音串被丢弃」被实测否定 （0000、zzzz 都命中）。这同时反证了 njcode.a 的解读 —— 那 285 条十六进制码点读法不是特例，而是引擎支持「任意串读法」的正常用法。 → 推论：任意编码的快捷输入都可行（数字编码、自定义快捷词），是明确的扩展方向。
② 大前缀下的「看起来没生效」是排序与候选数量问题，不是覆盖失败。 sha 有 1,827 条候选、shal 只剩 27 条 —— 判断覆盖是否生效必须用「唯一前缀」，不能用几千条候选的大前缀。

顺带修掉一个会露馅的问题：简拼串与同词全拼撞车。 阿呆 全拼 adai、简拼 ad —— 打 ad 时 全拼前缀与简拼条目各命中一次，「阿呆」在候选里出现两次。 这与 §6.7-② 修掉的 4,316 重复键是同类问题，只是跨读法。

  • 判定条件：简拼串是该词「其它读法」的前缀 ⟺ 会重复。 （不能用「是任意读法的前缀」—— 那条太宽，会把 sed→塞尔达 误判， 因为「塞尔达」自己的读法 saierda 并不以 sed 开头。）
  • 规模：full 包 60,000 条里 295 条（0.5%）会重复，293 条是 2 字母。 几乎全是首字零声母的词（阿X / 按X / 沙盒 shahe）—— 因为首字拼音只有 a/e/o 一个字母时，简拼前两位正好等于全拼前两位。
  • 处理：生成时直接丢弃（--abbrev-allow-dup 可关）。 零功能损失 —— 按定义，被丢的条目其全拼已以该串为前缀、优先级相同 → 候选位置不变，用户看到的东西完全一样。丢弃后会重复候选 = 0。
  • 产物：abbr-test.a（150,297 条 / +297）、 abbr-probe.a（150,299 条 / +297＋2 探针）、 abbr-full.a（210,000 条 / +60,000，4.64 MB，待实机确认大小）。 三份的唯一表记数都与完整版相同（149,030）—— 简拼只加读法入口、不加新词。
  • 实现要点：字→拼音表从设备自己的 njtan.a 提取 （12,873 汉字 / 707 多音字），口径强一致；多音字出多解 （「独立游戏」→ dlyx/dlyh）；只对长度 ≥ 2 字的词生成。

8 · 方法论与可复现性

解密链路（全部移植自 hactool 源码，非猜测）

头部前 0xC00 AES-XTS，tweak = BE(sector)，sector 从 0 起
section 偏移media_start × 0x200，不加 0xC00
key indexmax(0x206, 0x220) − 1 ← 最初解不开的主因
key areaAES-ECB-Dec(key_area_key_<name>_<idx>, …)
data key固定 decrypted_key_area[2]
CTR IVreverse(section_ctr[0:8]) ∥ BE(offset>>4)（双段拼接）
IVFC 头FS header +0x08；level_headers[i] 在 +0x10 + i*0x18
RomFS 定位romfs_offset = level_headers[5].logical_offset
NSO 分段单块原始 LZ4（整段一次解压），无 64K 分块链、无 8 字节前缀

已踩过并已修正的坑

  • Yaz0 没有结束标记。00 00 是合法回引用（dist=1，重复上一字节 18 次）； 误判为 EOF 会把 41 条流截断到几十字节。
  • PFS0 条目布局因固件而异。22.x 的 system title 用 0x18 字节 / 三个 u64， 老版 hactool 是 0x10 字节 / 四个 u32。需按「entry0.offset==0 且 entry1.offset==entry0.size」自动判定。
  • RomFS 的 parent/child/sibling/file 是字节偏移不是索引； 且区域顺序不固定（0805 实际是 header → data → …meta）。
  • SARC 节点从 SFAT + header_size(0x0C) 起，不是 +8。
  • section 数据不以 PFS0/IVFC magic 开头 —— FS superblock 在 NCA 头里，不能拿「magic 在 offset 0」当解密成功判据。
  • 用 META 找 npdm 时，代码段里也有 META 字节会误命中； 必须走 PFS0 文件表定位 main.npdm。
  • 别把「某类文件的特征值」当成「格式规范」。0x20==1146 / 0x44==1144 / 0x0c==大小−112 只是干净版式那一类的特征 —— 照抄进校验器，会把原版 njubase3（81726）、njtan（57895）、njexyomi（头长 60） 全部误判为坏文件。通用关系只有 0x0c = 文件大小 − 28 − 头部长度。 校验器坏掉比文件坏掉更危险：用户看到 FAIL 第一反应是「文件坏了」。
  • 「本工程写法」必须与「规范」分开。尾部表成对相同、读法全 a-z 都是本工程的写法约定， 原版 njcode（记号词典，285 条读法全非字母）两项全不满足、却完全正常 → 校验器对这类项应只报告比例、不判 FAIL。
  • 统计量要在正确的时点采样。去重计数放在填充之后计算，len(三组) − len(pick) 恒为负、被 max(0,·) 抹成 0，打印出「跨组去重 -0」的假象， 掩盖了真实的 4,317 条重复（用户打 ling 时「零」连出三次）。 交叉验证要换独立手段（直接解析产物去数重复键），不能只看程序自报。
